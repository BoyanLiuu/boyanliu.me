Snapmark is a screenshot annotator that runs entirely in the browser. Open an image, mark it up, press `⌘C`, and paste a full-resolution PNG wherever you were going to paste it. Nothing is uploaded, and there is no account to make.

## What it does

- **Six tools:** select, rectangle, arrow, highlighter that multiplies so what is under it stays readable, text labels on a legibility plate, and a pixelate region that is recomputed from the original on every draw, so it stays editable rather than being burned in.
- **Zoom to the pixel:** 10% to 800%, anchored at the pointer, with the image's own pixel grid showing past 200%. Space-drag, the middle button or two fingers pan.
- **Edit what you drew:** select one or many, move, resize by eight handles, nudge by a single pixel, reorder or hide layers, and undo by operation — one drag is one step, not forty.
- **Copy and export:** `⌘C` puts a PNG on the clipboard at the image's own size, or downloads it where the browser offers no clipboard. The export page also offers JPEG, or the annotations as W3C Web Annotation JSON that can be dropped back onto the same image later.
- **Kept in this browser:** each image and its annotations are filed under the SHA-256 of its bytes in IndexedDB, so reopening the same file brings its annotations back whatever it has been renamed to.
- **Reachable by address, keyboard and phone:** every screen has a URL, every shortcut the panel lists works, and the whole loop fits a 375px viewport by touch.

## What I wanted to learn

Three things, and the technology was chosen to force all three: **Canvas 2D, coordinate transforms, and export rendering.**

That ruled out the sensible option. Konva or Fabric would have finished this product in two evenings — and removed every one of the goals, because the handle maths, the hit testing and the export would all have been theirs. So the canvas work is written by hand: about eighty lines of hit testing, the resize-anchor maths, and arrowheads that stay in proportion at any shaft length.

## The one decision everything else follows from

Annotation geometry is stored **only in image space**, as unrounded floats. Nothing in the document model knows the zoom, the viewport size, or the device pixel ratio.

Storing geometry in view space is the obvious thing to do, because view coordinates are what a pointer event hands you. It also means every export is correct only at the zoom the annotation was drawn at — and the fix is not local. It needs a migration of every saved document plus a rewrite of every hit test, every resize handler and every draw function. The three spaces had to be separated on day one, in one module, with a test, before any tool code existed.

A second rule falls out of the first: **geometry in image space, affordances in screen space.** A resize handle is 8 CSS pixels whether you are at 10% or 800%; the click-versus-drag threshold is 3; the hit tolerance is 6. All three are converted into image pixels at the moment of use and never stored. Store a handle size in image pixels and the handles vanish at low zoom and swallow the screen at high zoom.

## Things that only break on someone else's machine

- **Two matrices, not one.** The transform handed to `ctx.setTransform` folds in `devicePixelRatio`; the one used to read pointer events must not, because `clientX` is already in CSS pixels. Use the wrong one for hit testing and every click lands at half its intended position — on a Retina laptop, and nowhere else. `setTransform` is therefore called in exactly one file, and that file is the only reader of `devicePixelRatio`.
- **Canvases fail silently.** Every engine caps canvas dimensions and total area, and over the cap you get no exception — just a blank or fully transparent image. A 108 MP photo exports fine on desktop Chrome and produces an empty PNG on an iPad. So the exporter reads a per-platform cap instead of probing, scales the scene to fit, and says what the real output size will be.
- **Safari loses user activation across `await`.** Render the blob, await it, then write to the clipboard, and the write is rejected because the gesture has expired. `ClipboardItem` has to be handed the _promise_, synchronously from the click.
- **`toDataURL` is the wrong call.** It blocks the main thread for several hundred milliseconds on an 8 MP PNG, returns a base64 string a third larger than the bytes, and on very large canvases can exceed the engine's maximum string length and quietly return nothing. `convertToBlob` is async, binary, and goes straight into a `ClipboardItem`.
- **Phone photos arrive rotated.** `createImageBitmap(blob, { imageOrientation: "from-image" })` normalises EXIF orientation at decode, so image space matches what the user sees. Without it every annotation lands rotated 90° in the export.

## The test that proves the architecture

Draw the same rectangle at 25% zoom. Draw it again at 400%. Export both. The two PNGs must be byte-identical.

It is the only test that catches a view-space value having leaked into stored geometry, which is the one bug in this project that is expensive to fix later rather than merely annoying. Everything else — 61 unit tests and 124 browser tests across 18 files, run at both 1× and 2× device pixel ratio — is there to keep that invariant from eroding.
